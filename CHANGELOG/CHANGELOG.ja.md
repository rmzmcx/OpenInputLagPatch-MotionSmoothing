# 更新履歴

[簡体字中国語](CHANGELOG.zh-CN.md) | [English](CHANGELOG.en.md) | 日本語

本ファイルは、上流の [OpenInputLagPatch](https://github.com/khang06/OpenInputLagPatch) に対する変更を記録します。

ゲーム内で実際に動作を確認済みの変更だけを記録するため、本ファイルは「どの修正が本当に検証されたか」の証拠でもあります。

## 2026-11-01

### 追加

- **弾幕アマノジャク（th14.3）のフレーム補間に対応**（`61b5021`）

  th14.3 には独自の3つのシーンフレーム関数と Present ポイントがあります。これらを引き継ぎ、
  追加の表示ではシーンのレンダリングだけを再生し、元の Present 設定を迂回します。ロジック、タイマー、
  入力、replay 状態、スクリーンショット、アイテムカード、ステージスクリプトはゲーム自身のフレームで
  進みます。追加描画ではシーンのビューポート、変換、関連する D3D 状態、テクスチャ、カメラ、
  スプライトキューの位置を保存して復元します。メニューテキストのレコード数も追加レンダリングの
  たびに復元し、重複した追加や描画を防ぎます。

  本作の thprac は GUI の更新と描画を同じ EndScene フックにまとめています。このフックを再実行すると
  ImGui が進み、ツール画面とゲーム画面が一緒にちらつきます。現在は C9 DX9 バックエンドの RVA と
  マシンコードを検証してから、描画パスだけを呼び出します。別のツールバージョンが読み込まれている
  場合は、overlay の再描画を安全に省略します。

  敵弾はゲーム自身の使用中マネージャーリストから読み取り、状態ごとの移動係数、レンダーフレームごとの
  ロジック更新回数、減速率、一時停止フラグに従って外挿します。自機は見えている論理位置から補間し、
  8つの option スロットと256個の自機火力登録スロットを実際のスプライトオブジェクトに解決したうえで、
  実際の描画位置を測定、外挿、復元します。直線レーザーと無限レーザーは実際の描画位置、角度、長さで
  測定し、角度差が正負の π をまたぐ場合は最短弧へ折り返します。`LaserBeamInf` の描画は空実装で、
  `LaserCurveInf` は要件どおり引き続き対象外です。

  180回/秒の表示で実測済みです。密集した敵弾、自機の移動、自機弾、直線レーザーはいずれも追加フレームを
  またいで動きます。最後のレーザーテストでは、92/92個の有効な Line/Infinite レーザーが投影経路に
  入り、論理フレームごとに3回表示され、実際には約180.6回/秒の表示になりました。一時停止、メニュー、
  読み込み中の黒画面、ステージ切り替え、スクリーンショット、replay 更新は反復経路の外にあります。
  追加フレームではシーンのレンダリングだけを再生するためです。

## 2026-10-31

### 追加

- **バレットフィリア達の闇市場（th18.5）のフレーム補間に対応**（`ce01d17`）

  th18.5 は th18 世代のタスクとレンダリング構造を使いますが、自機火力はアビリティカードから
  実行時に生成されます。主ショットと随伴ショットのスプライトハンドル、実際に表示されるオブジェクトは
  カード構成によって変わるため、th18 の固定スロットをそのまま流用できません。現在は2つのフレーム関数に
  あるレンダリングと Present ポイントを引き継ぎ、ゲーム自身のフレームはロジック、タイマー、入力、撮影、
  replay、カード更新を独占して進めます。追加 Present はレンダリングチェーンだけを再生し、メニュー
  テキスト数、ステージ遷移フィールド、ビューポート、スプライトキューの位置を復元します。追加描画中は
  フェードアウトオブジェクトの重複作成も抑止します。

  敵弾は6本のマネージャーリストと状態ごとの速度係数に従って前へ進めます。自機は見えている論理位置で
  内蔵アニメーションオブジェクトを駆動します。直線レーザーと無限レーザーはフレームごとに実測した位置、
  角度、長さで外挿します。カード火力はまずアビリティマネージャーの主ショットと随伴スプライトを対象にし、
  そのうえでそのフレームに実際に移動した描画スプライトを加えます。敵弾、自機、レーザーとの重複を除外し、
  同じオブジェクトを2回進めないようにします。180回/秒の表示で実測し、敵弾、自機、特殊な自機ショット、
  直線レーザーはいずれも追加フレームをまたいで動きました。一時停止、メニューテキスト、読み込み中の
  黒画面、ステージ切り替えは引き続きゲーム自身の論理フレームで進みます。

- **表示診断と `U` キーによる `oilp_display_diag.txt` 出力**（`d810ebb`）

  新しい診断では、モニターと DWM のリフレッシュレート、D3D8/D3D9 が実際に使用した表示パラメータ、
  直近600回の Present 間隔、Present のブロック時間を記録します。これにより、パッチが表示を提出して
  いない場合と、提出したもののリフレッシュレートやスワップモードの都合で目標時刻に表示できていない場合を
  区別できます。

### 修正

- **起動メッセージが中国語に対応し、名前を変更したゲームも識別可能**（`f824ac9`）

  すべての起動時および D3D 初期化時のメッセージは、Windows の表示言語またはシステムロケールに応じて
  中国語か英語を選ぶようになりました。実行ファイルのハッシュは引き続き正式な識別方法です。ハッシュが
  不明な場合は、ファイル名から対応する `th` と数字の組み合わせを探します。そのため `th15_n.exe` のような
  名前変更版でも起動でき、`th95`、`th128`、`th185` などは実際の th09.5、th12.8、th18.5 名へ対応付けた
  うえで非オリジナル版の警告を表示します。

  起動警告は以前、DLL 読み込みロックを保持した `DllMain` 内で実行され、ネストしたメッセージループが
  ときどきウィンドウを応答なしにしていました。現在はメッセージを先にキューへ入れ、ゲームスレッドが最初に
  `CreateMutex` または `CreateWindowEx` を呼び出したときに表示します。識別できないゲームも、ユーザーが
  確認するまで終了しません。

- **実際の表示レートが未計測の間は `0.0 fps` を表示しない**（`ce01d17`）

  D3D8 と D3D9 の overlay は以前、最初の0.5秒サンプルが終わる前や、ゲームが追加表示を利用していない
  場合に `0.0 fps` をそのまま描いていました。現在は0より大きい実測値が得られてからこの行を描きます。
  th18.5 の overlay も、ほかの補間対応作品と同じ左下配置に変更しました。

## 2026-10-30

### 修正

- **東方妖々夢の回転レーザーを最短弧で補間し、スクリプトによる跳びを除外**（`95a79e3`）

  th07 は ECL が更新するレーザー角度を正負の π の範囲に保存します。境界をまたぐと元のフレーム差分が
  2π に近くなり、追加フレームでは小さな回転が画面全体を掃いてから跳び戻るように描かれます。現在は角度差を
  先に最短弧へ折り、投影後に同じ範囲へ戻します。ECL が角度を直接設定した場合や、プレイヤーへ再照準して
  生じる1フレームの大きな跳びは連続運動ではないため、45度を超える角度変化は補間しません。実機で
  `大合葬「霊車コンチェルトグロッソ怪」`と`「反魂蝶 -八分咲-」`が正常なことを確認しました。

## 2026-10-27

### 修正

- **東方風神録の Marisa C がフォーカス保持中にオプションを余計に進めない**（`37c60a6`）

  Marisa C はフォーカス中にオプションが凍結し、フォーカスを離した後も戻り移動が始まるまで少しの間
  凍結を保持します。以前はこの保持フレームでも前フレームで測った移動量から追加フレームを作っていたため、
  フォーカスを素早く切り替えるとオプションが一瞬前へ飛びました。現在はゲーム自身の保持タイマーがまだ
  有効な間だけ、そのフレームのオプション移動量をゼロとして扱います。高速移動と、遅れて始まる戻り移動は
  引き続き正常に補間されます。

## 2026-10-23

### 追加

- **東方文花帖のフレーム補間に対応**（`851a9ff`、`cd408d8`、`31fe6d5`）

  th09.5 は計算、描画、写真処理を同じフレーム経路に置いています。この経路をそのまま追加フレームの描画に
  再利用するとタイマーが進み、2回目の撮影要求が発生する可能性もあります。そのためゲーム自身のフレームを
  唯一のロジックフレームとし、追加表示はデバイスの Present を使うように変更しました。敵弾はゲーム自身の
  1600個の固定スロットと6本のレイヤーリストから測定します。直線レーザーは `LaserInf` オブジェクトリストから
  位置、角度、2種類の具象クラスの表示スケールフィールドを測定します。`PlayerBody` は自機カメラ子オブジェクトが
  管理する5つの位置を通じて、自機本体と、自機に追従する4組のオプション/撮影コンポーネントを扱います。
  本作には自機弾オブジェクト群がないため、`PlayerShots` は意図的に何も移動しません。

  撮影要求と `snapshot/th###.bmp` の書き込みは引き続きゲーム自身の Present 末尾で、すべての追加表示より前に
  完了します。シャッター、HUD、スコア文字、写真欄、BOSS/敵本体は移動しません。追加描画では Present 後の
  ライブシーンを保存し、描画開始前にゲーム自身の描画パス開始時の状態へ戻し、描画後にライブ状態を復元します。
  ユーザーが出力した300フレームの診断では、ステージ内の各フレームが3回表示、間隔が5.56/11.11 ms、
  ゲーム自身のフレームレートが60.01、処理落ち率が0、敵弾リスト/有効スロット/マネージャー数が101/101/101、
  写真状態の変化が0でした。

## 2026-10-20

### 修正

- **th10～th20 のボス前転場がゲーム本来の速度へ戻る**（`45d099e`）

  th10 から th20 までは、一部の転場状態を**描画コールバック**内で進めています。ある描画コールバックは
  表示のたびにボス前タイマーを1減らし、別のコールバックはタイマーが30未満になると30フレームのフェードアウトを
  新規作成します。ゲームは1フレームに1回しか描画しないため、本来は1フレームにつき1回です。追加表示で
  描画チェーンをもう一度実行すると、1ゲームフレームでタイマーが2～3回減り、同じフレームに複数のフェード
  オブジェクトが作られることもありました。その結果、120/180/300fps では転場がそれぞれ2～3倍速くなりました。
  フェードオブジェクト自体に問題はなく、それぞれのタイマーは更新チェーン上で1フレームごとに+1されます。

  現在は追加描画ごとにステージオブジェクトの転場フィールドだけを保存/復元し、追加描画中はフェードの新規作成を
  省略します。転場フィールドだけをコピーし、オブジェクト全体はコピーしません。描画パスがオブジェクト内の
  ポインターを置き換える可能性があり、オブジェクト全体の保存/復元は th16/th18 で次の面を読み込む際の
  クラッシュを起こしたことがあります。また th16/th18 のインラインフェード割り当ては null を確認しないため、
  割り当て失敗ではなく作成分岐をトランポリンに変更しました。

  各作品のフェード作成位置とオブジェクトサイズ：th10 `0x402A61`、`0x2B64`；th11 `0x40335B`、`0x3158`；
  th12 `0x40391D`、`0x3724`；th13 `0x406FA8`、`0x41C0`；th14 `0x40E513`、`0x43A0`；
  th15 `0x40EA1A`、`0x6788`；th16 の分岐 `0x40A1B2`、`0x66F0`；th17 `0x40A77D`、`0x67B8`；
  th18 の分岐 `0x41C488`、`0x34A0`；th19 `0x4EC75B`（7引数 fastcall）、`0x3638`；
  th20 `0x472FE8`（cdecl）、`0x336C`。

- **th08 の回転レーザーを最短弧で補間**（`9adc923`）

  レーザー角度は保存時に `±π` へ正規化され（ECL opcode `0x41BDA5` が `FUN_0043EDB0` を呼び出し）、
  境界をまたぐと元のフレーム差分が `2π` に近くなります。追加フレームがこの差分をそのまま外挿すると、
  横向きのレーザーが1フレームで反転して見えました（4B の Star Typhoon が最も顕著です）。現在は角度差を
  先に最短弧へ折り、投影結果を元の範囲へ戻します：
  `theta = Wrap(theta1 + t * Wrap(theta2 - theta1))`。スクリプトが `startOffset`/`endOffset` を
  一度に変更した場合は運動として扱わず、引き続き補間しません。

- **th08 の5面 BOSS のぼかし効果が背景 tint を保持**（`9adc923`）

  5面 BOSS のぼかし効果は `FUN_00409160` で背景 tint を設定します（`g_Background` は `0x4E4030`、
  色は `+0x6468`、有効化は `+0x646C`）。背景描画はこれを使った後、保存していた色を灰色へ戻します。
  そのため追加表示ではぼかし色ではなく灰色の既定値が適用され、背景が両者の間で連続してちらつきました。
  現在は追加描画のたびにゲーム自身の描画開始時の tint を復元し、描画後にゲーム自身の描画が残した状態へ
  戻します。
  現在は追加描画の前後で2つのステージオブジェクト（`0x3158` バイト、アロケーターが使用するサイズ）を
  保存/復元し、追加描画中は `0x40335B` での新規作成を省略します。追加フレームはゲーム自身のフレームで
  既に作成済みのフェードを描きます。

- **overlay の2行の表示値が補間状態に依存しなくなる**（`1967235`）

  `ShowOverlay=1` は実際の表示レートだけを表示する設定です。以前も空の描画時間行が幅2ピクセルの黒い背景を
  残していました。しかしこの背景を省略すると、フレームレート行が依存するストリーム、インデックス、FVF、
  フォントテクスチャのバインドまで一緒に省略され、補間有効時に overlay 全体が消えました。現在は D3D8 と
  D3D9 の両 overlay が共有テキスト描画パイプラインを先にバインドし、各行に文字があるかどうかで背景を描くかを
  決めます。4つの `ShowOverlay` 値はすべて補間スイッチと無関係になり、黒点も増えません。

### 追加

- **補間対象を個別に選択でき、グローバル既定設定にも対応**（`4539e38`）

  以前の補間マスタースイッチは、すべてのオブジェクトを外挿するかどうかだけを決めていました。新しい最上位の
  `[Interpolation]` セクションは `Interpolation` をマスタースイッチとして残し、既定で有効な `PlayerBody`、
  `PlayerShots`、`BulletsAndLasers` を追加します。自機スイッチは自機本体、option、orb、子機を含み、残り2つは
  それぞれ自機弾と、敵弾および直線レーザーを制御します。各作品には元からこれらのグループごとの前進/復元経路が
  あるため、子スイッチは既存の測定式外挿だけを制御し、別のレンダリングやロジックモデルを追加しません。
  古い設定の `[Option] Interpolation` も引き続き読み取れます。

  パッチは
  `%APPDATA%\ShanghaiAlice\oilp_custom\openinputlagpatch.ini` を作成してグローバル既定設定として読み込み、
  その後でゲームディレクトリの ini に実際に存在するキーで上書きします。自動生成されるグローバルファイルは
  DLL に埋め込まれたバイリンガル参考設定から作られるため、完全なコメントを保持し、既存のユーザー設定ファイルを
  黙って上書きしません。

## 2026-10-18

### 修正

- **追加表示でも画面揺れを保持**（`9786d72`、`13eaa9c`、`8f150b0`）

  11作品は計算チェーンで画面揺れを設定し、描画時に読み取り、**自身の描画パス内で**それをゼロにします。
  「1フレームに1回だけ描画する」ゲームでは正しい動作ですが、追加表示はゼロにされた後の値から始まります。
  1フレームに3回表示すると1枚だけが揺れ、残り2枚は静止するため、揺れ幅が数分の1になったように見えます
  （th11、th13、th15～th18 が最も顕著です）。現在はゲーム自身の描画開始時の値を追加描画のたびに書き戻し、
  描画後にその描画パスが残した値へ戻します。対象は th08 の `AnmManager::screenShakeOffset`（`+0x1C`）、
  th10 `0x491E64`、th11 `0x4C379C`、th12 `0x4CEE04`、th13 `0x4DCBE8`、th14 `0x4D93B8` と `0x4D9610`、
  th15 `0x4E7E90`、th16 `0x4C1788`、th17 `0x4B6198`、th18 `0x4CD574`、th20 の2組の背景レイヤーオフセットです。
  各アドレスは、まず「ゲーム自身の描画パス」と「追加描画パス」がデバイスへ渡す頂点を比較し、書き込み可能な
  データの差分から特定しました。その後、ゲーム自身のコードへ戻り、書き込む関数、描画時に読み取る経路、

  1つでもディスク読み込みやシーン切り替えの停止に重なると、ゲーム全体の処理落ち率がその1回に引きずられました。
  短いステージや、長く演出画面にいた場合は数%の値が出ます。vpatch の `CalcFPS=1` はこの測定を丸ごと迂回し
  （ゲームのフレームレート関数を引き継ぎ）、vpatch 適用済みゲームでは常に0.00%になります。本パッチも同じ考えで
  `CalcFPS`（既定1、vpatch と同じ）を追加しましたが、ゲームへ渡すのは**フレームリミッターの実測値**なので、
  実際にフレームを落とすマシンでは正しく上昇し、0へ固定されません。フレーム計数は `Limiter::Tick()`
  （ゲームフレームごとにちょうど1回で、追加表示は通りません）に置くため、補間の追加表示がこの値へ入ることは
  ありません。

### 修正

- **replay 保存時のクラッシュ：入力パッチの「フラグ読み取り」が「アドレス読み取り」にコンパイルされた**（`23c5b6a`）

  vpatch の入力パッチを移植した際、`0x442CD9`（妖々夢）と `0x452319`（永夜抄）の「ゲームフラグワードを eax へ
  読む」命令をインラインアセンブリ `mov eax, dword ptr [0062F648h]` で書きました。しかしこのコンパイラーは角括弧内の
  絶対アドレスを**数値そのもの**と解釈し、`mov eax, 62F648h`（`A1 …` ではなく `B8 …`）を生成しました。
  ゲームへ渡された「ステージ内にいるか」の判定値は定数になり、妖々夢ではその定数の bit 2 がたまたま0でした。
  その結果、リプレイ記録側は毎フレーム「ステージ内ではない」出口から戻り、**1フレームも記録しませんでした**。
  ステージ終了時の `StopRecording` は入力用の2ポインターだけを補い、fps 用の2つには触れません
  （`mgr+0x88` / `mgr+0xA8` はリプレイ記録側の本体だけが書きます）。保存時の `SaveReplay` 第2段の `rep movs`
  （`0x443FCA`）は `stageFpsDataPointers[i] - stageFpsData[i].data` から約 -400MB の長さを計算し、範囲外アクセスで
  クラッシュしました（イベントログの `0xC0000005 @ 0x43FCA`）。永夜抄側も同じ書き方でしたが、その定数の bit 2 が
  偶然1だったため、「フラグを読み違える」だけでした。現在は C 関数でアドレスを読むよう変更し
  （`th7_game_flags` / `th8_game_flags`）、ソースに教訓も残しています：**インラインアセンブリで絶対アドレスを
  メモリオペランドにしない**。

- **永夜抄の処理落ち率が追加表示で壊れる：`lagDenominator` の保存漏れ**（`6a0916a`）

  永夜抄の「どれだけフレームレートを落としたか」は `lagNumerator`（`0x17CE8E8`）を `lagDenominator`
  （`0x17CE8EC`）で割った値で、描画チェーンのコールバック `Supervisor::CalculateFps`（`0x446F53`）が累積します。
  追加表示の前後ではこの関数の状態を保存/復元していましたが、一覧から分母が漏れていました。分母は描画パスごとに
  `+60.0` され、分子の分は0.5秒窓が閉じたときだけ加算されるため、比が約3倍に歪み、リザルト画面とリプレイの
  処理落ち率がどちらも誤っていました（妖々夢は該当する組をまとめて保存するため問題ありません）。確認方法は、
  その関数区間内で絶対アドレスを書く命令を**すべて**列挙して照合することです。修正後、diag では
  `numerator 16080.00 denominator 16080.00 ratio 1.0000` が読み取れます。

- **永夜抄の弾の時間停止判定と状態係数**（`538d885`）：弾の投影は以前、すべての状態で同じ係数を使い、
  ゲーム自身の「時間停止中は飛行中の弾だけ動かない」動作（`0x431490` が `g_GameManager.isTimeStopped` を読む）
  も再現していませんでした。現在は状態ごとに 1 / 1/2 / 0.4 / 1/3 / 1/2 の5係数を使い、`state == 1` かつ
  時間停止中は投影量を0にします。妖々夢側にも同じ時間停止ガードを追加しました（咲夜の雷）。

- **東方永夜抄（th08）のフレーム補間にも対応**（`b16284a`、`1cb0da0`、`6966ba0`、`4f95ade`、`0479b21`）

  永夜抄はさらに古い世代のエンジンで、1フレームは `GameWindow::Render`（`0x441E70`）1回です。入力は計算チェーン
  冒頭（`0x441F48`）で読み、フレーム全体を1つの描画ブロック（`0x441FB4..0x442027`）で描き、その後に1回表示します
  （`0x44203D`）。パッチはウィンドウ更新のフックからこのフレームをペーシングするため、追加表示はゲーム自身の
  表示後、次フレーム開始前に置かれます。形は th19/th20 と同じです。今回新しいのは、**表示レートと追加フレーム数を
  limiter が一括計算する**ようになった点です（th10～th20 の各コピーは今回は変更していません）。

  この形に加えて、本作では描くもののほとんどが**描画時点で描画コードにより状態をスプライトへ書き込みます**。
  自機のスプライトは描く瞬間に自機位置で配置され（`0x44D568..0x44D5B9`）、自機弾と子機も同様です。そのため
  追加フレームでは、自機は**描画する命令そのもの**で処理し、自機弾と子機は**それぞれの位置を移動**してから描画に
  読ませます。弾と同じ経路で、ゲーム自身の mover も `位置 += 速度`（`0x410A70`）です。自機描画の呼び出し規約には
  特に注意が必要です。AnmManager 自身の描画と同じ形で、**マネージャーは ECX、スプライト VM は呼び出し側がスタックへ
  積む引数、関数自身が `ret 4` で戻す**（`0x462FF0`）ためです。別の規約でフックすると、ECX の中身をスプライトとして
  扱い、スタックも4バイトずれ、自機テクスチャが消えます。そのためこのフックは手書きで、ソースにも
  **フック対象の関数先頭と `ret` を先に確認する**と明記しています。

  自機弾、子機、直線レーザーには読み取れる速度フィールドがありません（自機弾とレーザーはスクリプト駆動、子機は
  自機追従）。そのため「1フレームでどれだけ動いたか」はゲーム自身の描画パス内で**測定**し、追加フレームでは
  その何分の1かだけ前へ進めます。副次的な利点として、**動いていないものは誤って動かしようがありません**。
  スロット再利用（古い弾/レーザーが消え、同じスロットに新しいものが同フレームで生成される）をまたぐ場合は
  外挿しません（1フレームではあり得ない変位として読むためです）。今回自機弾に現れたズレはこれが原因でした。
  子機は4スロットで、描画コールバックが実行時に設定され、**5チームすべてが同じ描画関数**を使います（5チームとも
  確認済み）。診断ではそれらのアドレスを出力します。

  メニューと一時停止画面は**まったく処理不要**です。本作の文字列テーブルは**同じ描画パス内で描画後にクリア**され
  （低優先度の ascii パスが先に `OnDrawLowPrioImpl`、その後 `ResetStrings` を実行し、HUD は同じパス内の
  より早い段階で追加されます）、追加表示でその種の文字を二重に描くことはできません。

  また D3D8 のオーバーレイでも**実際の表示フレームレート**を表示できるようになりました（左下の描画時間行の右）。
  計数は D3D8 の present フックが行います。D3D9 オーバーレイが th10～th20 に表示している項目で、th08 が
  初めてこれを得た D3D8 作品です。

  実機確認（180Hz）：各フレームで3回表示、間隔5.56ms、1秒あたり180.6回。ゲーム自身のフレームレート表示は60の
  ままで、その行の文字も `60.00fps` のままです。弾、自機、自機弾、子機（5チーム）、直線レーザーはすべて滑らかで、
  跳び/残像/ズレはありません。thprac の入力遅延表示も補間追加前の位置へ戻りました。

  要件どおり**対象外**：敵本体（位置はアニメーションスクリプトで決まり、速度を読み取れません）と曲線レーザー。

- **4作品の直線レーザーを変位測定ではなく速度読み取りへ変更**（`7fdd8fd`）

  （数百発）ではほぼ確実に発生します。速度を読む方法にはこの問題がなく（発射物自身の速度を読み、予告線のような
  元から速度0のものは正しく動きません）、レーザーが出現した最初のフレームでも正しく外挿できます。

### 修正

- **一時停止/セーブ画面の文字が追加フレームで二重に描かれない**（`d387341`）

  **メニューと一時停止/セーブ画面の文字は「1回の走査で1行ずつ描く」方式ではありません。まずテキストオブジェクト内の
  レコードリストへレコードを追加し、その後「そのフレームで描画待ちのレコード数」だけリストを走査して描きます**
  （各レコード `0x138` バイト、上限 `0x140`）。この数は**毎フレーム1回リセット**され、そのリセットは
  **update 走査**内、つまり追加表示では再生されないゲームロジック側で起きます。そのため追加フレームはゲーム自身の
  フレームが残したレコードを**もう一度描き**、さらに自身のレコードを追加して重ねました。各フレームの**2番目の**
  追加フレームはゲームフレームが直前に使ったバックバッファへ描くため、2枚分が同じ画像に残ります。

  4作品のフィールドと症状（すべて各作品の逆アセンブルから読み取り）：

  | 作品 | テキストオブジェクト（グローバルポインター） | レコード配列 | **そのフレームの描画待ち数** | 症状 |
  |---|---|---|---|---|
  | th12 | `[0x4B43B8]` | `+0x97C` | `+0x18F7C` | レイアウト状態が変わらず、2枚が**完全に重なる**ため文字が少し濃く見えるだけ |
  | th13 | `[0x4C2160]` | `+0xB5C` | `+0x1915C` | 同じ行の文字が**2つ表示され、行に沿ってズレが増える** |
  | th14 | `[0x4DB520]` | `+0xBAC` | `+0x191AC` | th13 と同じ |
  | th15 | `[0x4E9A58]` | `+0xC20` | `+0x19220` | th12 と同じ |

  > **調査時の注意**：この症状は **120Hz では見えません**（各フレームの追加が1回だけで、差が1段階しかないため）。
  180/240Hz で顕著になります。また「ゲームフレーム + 1番目の追加フレーム」の2枚は差が非常に小さく、問題ないように
  見えます。確認する場合は**1フレーム内の各表示をすべてキャプチャー**して比較してください。

  修正は既存の「前進 → レンダリング → 即時復元」規律に従います。**ゲーム自身の描画走査が始まる前**にこの数を保存し
  （th13 は自身の走査で変更される12個のフィールドも保存：`+0x040` プール書き込みポインター、
  `+0x050/+0x054` レイアウト位置、`+0x3CC..+0x3E8` の8個の float、`+0x1915C` の数）、
  **各追加フレームの描画前に書き戻します**。追加フレームはリスト先頭から自身のレコードを再追加し、ゲームフレームと
  完全に同じ文字を描きます。終了後に残る状態もゲーム自身の1回分と同じで、次フレームのリセット動作にも影響しません。

  確定には**表示前のバックバッファを BMP として取得し、ピクセル単位で比較**しました（`GetBackBuffer` +
  `GetRenderTargetData` を使い、同じゲームフレーム内の各 Present をすべて保存）。修正前は2番目の追加フレームと
  ゲームフレームの差が2911ピクセル、平均チャンネル差 **109**（目視できる2行の文字）でしたが、1番目の追加フレームは
  差 **13.75** で正常に見えました。修正後は4作品とも**ピクセル単位で完全一致（差0）**となり、UI テキストが正常へ
  戻ったことを実測確認しました。

- **紺珠伝の補間を自機、子機、自機弾、直線レーザーまで拡張**（`14e0551`）

  弾だけが前進すると、追加表示は「画面の半分だけ動く」場面になります。弾は進みますが、自機、その横の子機、自機が撃つ弾、
  敵が設置した直線レーザーはゲーム自身が表示したフレームのまま繰り返されました。これらのオブジェクトには直接読める速度が
  ありません。自機は入力に従って動き、子機と自機弾は滑らかに追従し、レーザーは旋回しながら伸びます。そのためパッチでは
  **測定式**に変更し、毎ゲームフレーム、ゲーム自身の present 時に描画が実際に読むフィールドを前フレームと比較します。
  追加表示ではその差へフレーム内の小数部分を掛けて書き戻し、描画後に即座に復元します。動いていないもの（押しっぱなしで
  静止している、一時停止中）は自然に0になり、生成直後のオブジェクトやプールスロットが別オブジェクトへ再利用されたものは
  前フレームと比較できないため、そのフレームでは動かしません。

  動かすのは描画が実際に読むデータです。自機本体は自身の位置 `+0x618`（レンダリング時にアニメーションオブジェクトへ
  コピーされるため位置を変えれば画面も動きます）、子機と自機弾はアニメーションオブジェクト `+0x5EC` を直接変更します
  （位置は更新段階で書き終えています）。レーザーはレーザーマネージャー `[0x4E9BA0]` 自身のリストを使い、直線系
  （直線、無限、beam の3 vtable）だけを処理します。3種類とも位置 `+0x54`、角度 `+0x6C`、長さ `+0x70` を自身に持ち、
  これらは描画時に画面を組み立てるための値そのものです。曲線レーザーは要件どおり明確に対象外とし、マネージャー自身の
  センチネルノードは vtable がホワイトリストにないため省略されます。

  途中で2つの問題を踏み、どちらも修正しました。最初の版ではゲーム自身のスプライト検索関数を関数ポインターで呼びましたが、
  引数はスタック渡しでした。そのためアニメーションオブジェクトではないポインターを受け取り、そこへ位置を書いた結果、
  stage へ入るとゲームがクラッシュしました。また「前フレームの位置」を毎フレーム再構築される表へ保存していたため、差分が
  常に0になり、自機はまったく動かないように見えました。実測確認：自機、子機、自機弾のスプライトは正しく追跡されて動き、
  画面上の直線レーザー（テスト時12本）も見つけて前進できました。敵本体はまだ未対応で（stage 1 の最後の部分）、
  曲線レーザーも対象外のままです。

- **overlay が実際の表示フレームレートを表示**（`bad3516`）

  補間有効時は1ゲームフレームが複数回表示されるため、ゲーム自身のフレームレートは画面が実際に受け取ったコマを表しません。
  以前は追加フレームが均等に配置されているかを確認する方法がなく、`U` で診断ファイルを出力するしかありませんでした。
  現在は overlay に**実際の表示フレームレート**の行が増えます。これは表示そのもの（ゲーム自身の1回 + 各追加フレーム）を
  数えるため、設定で要求した値ではなく画面が実際に受け取った値を表示します。overlay と補間の両方が有効なときだけ現れ、
  補間オフではゲーム自身のフレームレートを繰り返すだけなので表示しません。0.5秒の窓で測り、数字が往復して跳ねないように
  しています。

  この行は**ゲーム領域の右端**へ描き、ウィンドウ右下角には置きません。右下角は thprac が自身のフレームレートと減速率を
  描く場所で、重なるためです。ゲーム自身の座標でアンカーを決め（640の画面では play field が幅384、x=32から始まるため
  右端は416）、overlay がバックバッファのサイズに合わせて拡大します。そのため1:1表示でも拡大表示でも画面の横に収まります。
  実測確認：表示値はゲーム領域の右側にあり、thprac の値を覆いません。`Interpolation = -1` の180Hzでは1ゲームフレームに
  約3.0回、毎秒180回と表示されました。アンカーは現在紺珠伝のレイアウトに合わせており、今後ほかの作品を補間する際は
  作品ごとの値を渡す必要があります。

- **ウィンドウモードへ `CoverTaskbar` を追加：タスクバーを退かせるが、ウィンドウを最前面へ固定しない**（`7104d0e`）

  タスクバーを覆うには topmost 層へ入る必要があり（タスクバー自身が topmost ウィンドウです）、`AlwaysOnTop` には
  「ゲームがほかのすべてのウィンドウを覆う」という副作用が常に付いていました。「画面いっぱいのボーダーレスウィンドウが
  欲しいだけで、タスクバーを見たくない」という用途には強すぎます。`CoverTaskbar` はこの2つを分離し、
  「ウィンドウがアクティブな間だけタスクバーを見せない」処理だけを行います。1はシェルへ全画面ウィンドウだと伝え
  （`ITaskbarList2::MarkFullscreenWindow`）、タスクバー側が退きますがウィンドウは通常のままで、別ウィンドウへ切り替えれば
  ゲームを覆います。2はウィンドウがアクティブな間だけ一時的に topmost 層へ入れ、プレイ中は `AlwaysOnTop` と同じで、
  別ウィンドウをアクティブにすると解除します。1でタスクバーオブジェクトを取得できない場合は2へフォールバックします。

  最初の版では最初のフレームを描く前にゲームが停止しました。原因は2つです。ゲームのウィンドウプロシージャを引き継いで
  アクティブ化を監視しましたが、ウィンドウ状態の変更が同じウィンドウプロシージャへメッセージを戻し
  （`SetWindowPos` は位置とアクティブ化変更を送り、シェルも応答します）、自身を再帰呼び出しして戻らなくなりました。
  またゲームスレッド上でシェルへタスクバーオブジェクトを要求していました。これはプロセス間呼び出しで、シェルが混雑すると
  長時間停止し、起動処理中では致命的です。現在は専用スレッドを1つ起動し、50msごとにどのウィンドウがアクティブか確認し、
  ウィンドウが実際に作成されてから操作します。結果が変わったときだけ呼び出し、停止し得る処理はすべてそのスレッド上に置き、
  ゲームスレッドはスレッドを起動するだけです。実測で問題ありませんでした。制約も明確で、ウィンドウがアクティブでない間は
  何もできません（非 topmost ウィンドウは定義上タスクバーの下になります）。つまり「プレイ中にタスクバーが見えない」ので
  あり、「常に絶対見えない」わけではありません。

### 修正

- **ゲームを再開すると自機（子機、自機弾を含む）の補間が黙って無効になる**（`8efd72f`）

  測定式外挿ではスプライトごとに「前フレームの位置」を記録し、キーは**スプライトのアドレス**です。スプライトが消えたときは
  「本当に消えた」のか「スロットが残っている」のか区別できないため、これらの記録は以前、追加されるだけで削除されませんでした。
  1回のゲーム中に自機弾のスプライトは次々と新しいアドレスを持つため、表が埋まると、表にないスプライトは記録を取得できず
  外挿に参加しません。自機本体は毎フレーム最初に登録されるため、最初のゲームでは必ず自身の記録に当たりました。しかし
  ESC+R でゲームを再開すると新しい自機オブジェクトが作られ、通常はアドレスが変わるため、**自機の補間が黙って無効**に
  なりました。「確率的」なのは malloc がたまたま新しい自機を旧アドレスへ置く場合があり、そのときは正常に動くためです。
  子機と自機弾も新しいアドレスになれば同様に無効になりました。

  現在は記録を回収できます。まず空きを使い、空きがなければ**そのフレームで使われていない**記録のうちフレーム番号が最も古い
  ものを回収します（最も古い記録は前フレームで測れておらず、元々差を計算できません）。そのフレームで使用中の記録は絶対に
  回収しないため、動いているスプライトの記録が奪われることはありません。レーザーの記録も同様です（レーザーは個別に
  malloc/free されるためアドレスも移動します）。紺珠伝の実装にも同じ問題があり、まとめて修正しました。診断ファイルには
  `player: N sprite(s) this frame had no movement record` の行が増え、正常時は常に0です。

- **紺珠伝のフレーム補間に対応**（`641f5ac`、`7456449`）

  ゲームは引き続き自身のフレームレートでロジックを実行しますが、各フレームが複数回表示されます。60fps のロジックを
  180Hz で表示すると、0、半フレーム、1フレームの位置でそれぞれ1回表示します。新しい `Interpolation` オプション
  （既定は無効）がこれを行います。追加表示はゲームが既に計算した状態を描くため、その中で何かが動かなければ意味が
  ありません。パッチは追加表示の前に弾を「速度 × その表示が表すフレーム内の小数部分」だけ前へ進め、レンダリング後に
  即座に戻します。これはゲーム自身が2フレーム間で弾に加える移動そのもので、ゲーム自身のロジックは前進させた位置を
  一度も見ません。

  追加表示ではデバイス自身の `Present` を使います。これはツールが置き換える前に取得したものです。thprac の Present
  フックは「1ゲームフレームに1回表示」として入力遅延を測るため、追加表示まで受け取ると表示値が1フレームの何分の1かに
  なります。また表示を繰り返すと、ツールがそのフレームで既に描いた overlay が消えます（thprac はオブジェクト描画から
  戻った位置で ImGui overlay を描きます）。そこでパッチは実行時に「このフレームで既に構築済み」の変数を見つけ、
  各追加表示の前に戻します。こうすると追加表示ごとに構築済み overlay を再描画でき、ツール自身のコードを走らせません。
  ツールのコードを再実行すると ImGui のキーリピートが表示ごとに進み、方向キーを押しっぱなしにするとメニューが何段も
  飛びます。

  弾は、ゲーム自身が弾用に作成したマネージャー（`bullet.anm` を読み込み、stage 開始時に作られるもの）から取得し、
  スプライトの見た目で弾らしいものを探すことはしません。これによりゲーム自身の弾を正確に取得できます。敵弾は画面の
  ほかのものが共用するスプライトオブジェクトではなく、マネージャーリスト上の別の、より大きなオブジェクトで、位置と
  フレームごとの変位は互いに隣接する別のオフセットにあります。実測確認：表示は180Hzに均等に配置され、ゲーム自身の
  フレームレートは変わらず、弾は追加フレーム間で確かに動きます（診断ファイルでは画面上の弾がすべて前進として
  数えられます）。一時停止画面、メニュー、thprac の overlay、遅延表示も正常でした。敵と直線レーザーはまだ前進させて
  おらず（それぞれ後続の段階）、曲線レーザーは完全に対象外です。

- **東方獣王園（th19）v1.10c に対応**（`0c8a926`）

  th19 は D3D9 ゲームなので D3D9 側の仕組みを使います。overlay、D3D9Ex への更新、フレームレートリミッターです。

- **th19/th20 に丸1フレーム分の入力遅延が余計に発生し、overlay も本来の値を表示しない**（`18e1b2f`）

  この2作品のフレームはゲーム内蔵のフレームレートリミッターではなく、ゲーム自身の時計でペーシングされます。
  以前は D3D9 の EndScene フックで limiter を tick していましたが、EndScene は present より前に起きるため、待機が
  「入力読み取り」と「画面 present」の間に挟まれました。その結果 thprac の遅延表示は丸1フレーム（約16ms）でしたが、
  ゲームが実際に必要とするのは約1msでした。

  現在はゲーム自身が待機する位置、前フレームの present 後かつ今フレームの入力読み取り前に待機します。さらにゲームが
  既に計算した値を使います。ゲーム自身の `Sleep(1)` 呼び出し前には「この時計の次の締切までどれだけあるか」が既に
  置かれているため、ゲームの時計がフレーム開始と判断する時刻ちょうどに待機を終えられ、両者の位相差も発生しません。
  この待機はゲーム本来の `Sleep(1)` より正確で、ときどき出ていた2.5msの遅延スパイクも解消しました。overlay には
  ゲーム自身の処理時間（thprac が表示する値）が出て、丸1フレームではなくなりました。また2作品とも `BltPrepareTime` の
  影響を受けません。待機はパッチ自身のスケジュールではなく、ゲーム自身の時計を基準にするためです。

- **60の整数倍のリフレッシュレートを持つ表示モードがない場合でもゲームを終了しない**（`0c8a926`）

  `FullscreenRefreshRate = 2`（既定）は、選択した解像度で60の整数倍のうち最も高いリフレッシュレートを選びます。
  そのようなモードが解像度にない場合、以前はメッセージボックスを表示してゲームを終了しました。現在は D3D8 側の経路と
  同じく、ランタイム自身にモードを選ばせます。

- **v1.6 で th06～th18 が超高速で動作する**（`5ea9c18`）

  limiter に th19/th20 向けとして追加した「同一フレーム内の重複除去」が、「1/4フレームより早く到着した tick」を現在

  limiter で待機し、`frame_start` は待機後に書かれるため、次の tick が測るのはゲーム自身の処理時間（通常1～2ms）に
  なります。その結果ほとんどのフレームで待機せず、超高速になり、`GameFPS` も効きませんでした。

  th19/th20 は `Limiter::TickUntil` を通り、この処理がないため影響を受けませんでした。現在はこの判定を削除し、
  旧作品の速度は正常へ戻っています。

## 2026-10-06

### 追加

- **D3D9 を通らない DX8 ゲームでも overlay を表示**（`d0cc56a`、`ed756d7`）

  以前の overlay は D3D9 版だけでした。D3D9 の CreateDevice フックで作り、EndScene フックで描くため、d3d8to9 と
  DXVK（D3D8 を D3D9 へ変換）では使えますが、dgVoodoo2（D3D8 を直接 D3D11 へ変換）や wrapper を入れない場合は
  表示できませんでした。ゲーム自身の D3D8 デバイスで描く overlay を追加し、「D3D9 デバイスがない」場合だけ有効に
  しています。D3D9 経由の wrapper は従来の overlay をそのまま使います。

- **`FullscreenRefreshRate` が DX8 ゲームでも有効**（`5d1d73f`）

  このオプションは以前 D3D9 フックにだけ存在し、DX8 作品にはまったく効きませんでした。DX8 作品は IDirect3D8 で表示
  パラメータを作り、ゲームは「現在のデスクトップリフレッシュレート」を要求するため、3つの値がどれも最高
  リフレッシュレートを強制しているように見えました。現在は D3D8 の CreateDevice/Reset フックでも同じロジックで
  リフレッシュレートを選びます。その解像度に適切なモードがない場合は、エラー終了せずランタイムに決定させます。

- **DX8 ゲームでも垂直同期を強制オフ**（`1dd1bb2`）

  `D3DPRESENT_INTERVAL_IMMEDIATE`（および `D3DSWAPEFFECT_DISCARD`、バックバッファ数0）の設定は以前 D3D9 フックだけで
  行われていたため、dgVoodoo2 や wrapper なしではゲームが要求した表示間隔のまま表示され、replay 早送りも
  リフレッシュレートに制限されていました。現在は D3D8 フックも同じ設定を行います（全画面のみ。D3D8 ではウィンドウ
  モード時に FullScreen_* の2フィールドを0のままにする必要があります）。

### 修正

- **排他的全画面の DX8 ゲームでウィンドウを離れて戻ると終了する**（`d0cc56a`）

  ゲームは自身の `D3DPOOL_DEFAULT` リソースを解放してから `Reset` を呼び、失敗するとメインループを終了します。
  D3D8 の Reset は DEFAULT プールのリソースが1つでも残っていると失敗しますが、overlay 自身のリソースは Reset 後に
  解放されていました。そのため全画面 DX8 ゲームはフォーカスを取り戻した時点で終了しました。

- **DX8 ゲームの一時停止中に overlay が一時停止画面の隅へ移動する**（`ed756d7`）

  状態ブロックには viewport が含まれず、overlay はゲームが現在設定している viewport を使って描画します。妖々夢の
  一時停止画面は画面をより小さな領域へ描くため、overlay がその隅へ移動しました。現在は描画のたびに自身の viewport と
  変換を再設定します。thprac の overlay と同じ方法です。

### 変更

- **「Direct3DCreate9 をフックできない」の通知をコンソール出力へ変更し、dgVoodoo2 を優先推奨**（`d4296fc`、`5df484c`）

  overlay とほかの DX8 設定が D3D9 に依存しなくなった後、D3D9 を通らない DX8 ゲームで失われるのは D3D9Ex の低遅延経路
  だけです。デバッグコンソールへ1行残す価値はありますが、起動のたびにダイアログで中断する必要はありません。推奨順は
  dgVoodoo2 を先に変更しました。コミュニティでの実測で flip モデル表示の遅延が最も低いためです。

- **参考設定をすべて既定値へ変更**（`dee2a1e`）

  `openinputlagpatch.ini` にはテスト用の値（`BltPrepareTime` 0、`Sleep` 0、ウィンドウモード関連など）が入り、
  ファイル自身のコメントに書かれた既定値と一致せず、比較しづらい状態でした。現在は22個のキーすべてが既定値と同じで、
  ファイルは「オプション一覧」の役割だけを持ち、何も有効にしません。README も dgVoodoo2 を優先推奨する内容へ更新しました。

## 2026-10-05

### 追加

- **ウィンドウモード：vpatch と同じ `[Window]` 設定と、起動時に全画面かどうかを確認する機能を追加**（`26b310a`）

  `openinputlagpatch.ini` に vpatch の `[Window]` セクションが追加されました。`AskWindowMode`、`enabled`、`X`、`Y`、
  `Width`、`Height`、`TitleBar`、`AlwaysOnTop` を持ち、意味は `vpatch.ini` と同じです。ゲームがウィンドウモードのときは
  これらの設定に従ってウィンドウを移動/サイズ変更し、タイトルバーと最前面設定を適用します。

  `AskWindowMode` を有効にすると、th06 から th09.5 までがウィンドウ作成前に全画面で起動するか確認するため、ゲーム自身の
  表示設定を変更する必要がありません。回答は vpatch と同じくゲーム自身の「ウィンドウモード」フラグへ書き込みます。
  D3D 表示パラメータだけを強制するわけではありません。dgVoodoo2 が排他的全画面をボーダーレスウィンドウへ変換する設定
  （`AppControlledScreenMode = false`、`FullscreenAttributes = fake`）ではその要求が無視され、ゲーム自身の設定が
  ウィンドウモードなら、そのままウィンドウモードとして動作します。

  確認ダイアログはゲームが単一インスタンス用ミューテックスを作成した直後、thprac などのツールがまだゲームを検出できる
  最も早いタイミングで表示されます。その後ゲーム内メニューでモードを切り替えても強制的に戻されません。確認が行われるのは
  th06 から th09.5 までだけです。それ以降の作品には同じ設定が元からあります。

## 2026-10-04

### 修正

- **dgVoodoo2 使用時に「couldn't hook Direct3DCreate9」警告を誤表示**（`d20a521`）

  dgVoodoo2 は D3D8 を D3D11 へ変換するため、その `d3d8.dll` にはフックできる `Direct3DCreate9` がありません。ゲームが
  完全に正常でもパッチが警告を表示していました。現在は読み込み済み `d3d8.dll` のバージョンリソースを読み
  （`ProductName` に `dgVoodoo` を含むか、すべての言語/コードページブロックを確認）、この場合だけ警告を省略します。
  不明な wrapper では従来どおり警告し、d3d8to9 は通常のフック経路を使います。

- **紅魔郷 + dgVoodoo2：加速時にフレームレートが画面のリフレッシュレートを超えない**（`667fe5e`）

  dgVoodoo2 はゲームの D3D8 表示を D3D11 の flip モデルスワップチェーンへ変換し、このスワップチェーンはキューが
  いっぱいになると次の垂直帰線までブロックします。ゲームロジックは1フレームにつき1回しか提出しないため、ゲーム速度が
  画面のリフレッシュレートへ固定され、replay 早送りと thprac の加速もそれ以上速くなりませんでした。現在は D3D8 の
  Present（vtable インデックス15）をフックし、目標フレームレートがリフレッシュレートより高い場合は
  `N = ceil(目標フレームレート / リフレッシュレート)` で提出を間引きます。通常のフレームレートでは N が1になり、
  すべての呼び出しをそのまま転送します。

  このフックは現在紅魔郷にだけ導入しています。この問題は同作固有に見えるためです。それ以降の作品は影響を受けず、
  D3D9 作品は別の表示経路を使います。

- **`AlwaysBlt` オプションを追加：ウィンドウが非アクティブでも描画を継続**（`12fe031`、`c41c53d`、`ea884df`）

  ウィンドウから切り替えて戻ると画面が止まる原因は2つありました。ゲーム自身がフォーカスを失うと描画を止める
  （`GameWindow::Render` が非アクティブ時に即座に戻る）、そして oilp のウィンドウ更新フックもフォーカス喪失時に
  即座に戻り、ゲーム本来のウィンドウ更新を呼びません。その更新が描画も駆動するため、画面がまったく描かれなくなります。

  現在 AlwaysBlt はその早期リターン判定を迂回し（th06 の `0x004206F0`、th07 の `0x004346F0` にある条件分岐を
  無条件分岐へ変更）、フォーカス喪失時もウィンドウ更新を続けます。動作は vpatch の AlwaysBlt オプションと同じです。
  既定で有効で、`openinputlagpatch.ini` の `AlwaysBlt` から無効にできます。リポジトリにも参考設定ファイルを同梱しています。

  実装は th06 と th07 のみです。
